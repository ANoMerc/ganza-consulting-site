# Ganza Consulting — как устроен этот сайт

Вы, вероятно, попали сюда, потому что рассматриваете меня как подрядчика и
решили сначала посмотреть код. Разумно: сайт консультанта — единственный его
артефакт, который можно проверить до подписания договора.

Поэтому это не инструкция по эксплуатации. Это разбор решений: что здесь
сделано, почему именно так и от чего я отказался. Инструкция — в самом конце,
она короткая.

---

## Что это

Статический сайт на двух языках: 52 страницы, 16 лонгридов по 8–10 минут в
каждой языковой версии, кейсы, прайсинг, шаблоны и чек-листы, политика
конфиденциальности, форма обратной связи, интерактивный калькулятор проекта и
собственная аналитика. Ноль фреймворков, ноль зависимостей в рантайме, ноль
сборщиков на JavaScript. Генератор — 1 200 строк Python, которые я написал бы
заново за день, потому что там нечего понимать.

Главная весит 145 КБ и делает 8 запросов. Лента блога с двенадцатью обложками
— 190 КБ. Все десять проверенных страниц проходят axe-core с правилами WCAG 2.1 AA без
единого нарушения.

## Три решения, ради которых стоит смотреть

### 1. Ядро и периферия разделены физически

Самое дорогое в поддержке сайта — не код, а то, что правки контента требуют
трогать код. Здесь этого нет: `Tools/` и `content/` разделены по признаку
«как часто меняется».

```
Tools/core/     ядро      меняется раз в квартал
  config.py       домен, бренд, контакты, языки, прайсинг
  theme.py        <head>, шапка, подвал, JSON-LD, вычисление путей
  blocks.py       блоки контента → HTML
  pages.py        сборка страницы из секций
  blog.py         лента, статья, RSS

content/        периферия  меняется каждую неделю
  pages/          описания страниц: что и в каком порядке собрать
  posts/          статьи
  cases/          кейсы
  blocks/         текстовые страницы и шаблоны — списками блоков
  fragments/      двуязычные куски вёрстки

assets/
  src/            авторские стили, скрипты и шрифты — то, что правят руками
  build/          склеенные бандлы и шрифты с хешем, генерируются сборкой
  img/            картинки и обложки статей
```

Разделение `src/` и `build/` появилось не ради порядка. Раньше страница тянула
четыре блокирующих CSS-файла и два скрипта; теперь `Tools/core/assets.py`
склеивает их в один бандл с хешем в имени, и остаётся один CSS-запрос вместо
четырёх. JS намеренно не минифицируется: без разбора синтаксиса это способ
однажды сломать продуктив ради двух килобайт, а гзип на отдаче делает основную
работу. Зависимостей у сборки от этого не прибавилось.

Практический смысл: чтобы поменять домен, я правлю одну строку в `config.py`
и запускаю сборку — обновляются canonical, hreflang, JSON-LD, sitemap, RSS и
Open Graph на всех 34 страницах. Чтобы добавить статью, я не открываю ни один
файл в `Tools/`.

Проверка на честность такого разделения простая: посмотрите, сколько мест
знает про конкретную страницу. Про страницу кейсов знает ровно один файл —
`content/pages/cases.py`, семнадцать строк. Ядро про неё не знает ничего.

### 2. Пути считаются, а не пишутся

Двуязычный сайт со вложенностью до трёх уровней — это место, где обычно
заводится ад из `../../..`. Здесь есть объект `Ctx`, который знает язык и
адрес страницы, и умеет считать все относительные пути от неё:

```python
ctx = Ctx("ru", "blog/when-not-to-automate/")
ctx.asset          # ../../../assets/     — до статики
ctx.to("cases/")   # ../../cases/         — до другой страницы того же языка
ctx.alt("en")      # ../../../blog/…/     — эта же страница на другом языке
ctx.abs()          # https://…/ru/blog/…/ — для canonical и sitemap
```

Ни в одном шаблоне нет ни одного захардкоженного `../`. Поэтому языковую
схему можно перевернуть тремя строками в конфиге: когда русскую версию
переносили из `/ru/` в корень, изменились три строки, а сборка сама
пересчитала все ссылки, canonical и hreflang и разложила шестнадцать
редиректов со старых адресов.

### 3. Разметка для поисковиков собирается из самой страницы

Обычная беда structured data — она пишется руками отдельно от контента и
через полгода расходится с тем, что видит человек. Здесь `FAQPage` для страницы
услуг собирается регулярным выражением **из реальной разметки секции FAQ**
(`content/fragments/faq.html`), а `wordCount` и `timeRequired` в `BlogPosting`
считаются по фактическому тексту статьи. Разойтись им негде: источник один.

Время чтения в интерфейсе — из того же расчёта, с разной скоростью для
русского и английского (180 и 200 слов в минуту), и сборка ругается, если
статья выпала из диапазона 7–15 минут.

## Что здесь сделано неочевидно

**Оформление — снимаемый слой.** Вся тема Liquid Glass живёт в
`assets/css/glass.css` и подключается последней. Она переопределяет только
материал: фон, границы, скругления, тени, цвет. Структура и сетки — в
`base.css`. Убрать одну строку из `theme.py` — вернётся исходный бруталистский
вид, вёрстка не поедет. Это дало возможность полностью сменить визуальный язык
сайта за один вечер, не трогая ни одного шаблона.

**Отзывчивость к настройкам пользователя.** `prefers-reduced-motion`
останавливает фон и убирает смещения при наведении. `prefers-reduced-transparency`
выключает размытие и делает панели плотными — без этого правила часть текста
стала бы нечитаемой, а не просто менее красивой. Ниже 900 пикселей
`backdrop-filter` остаётся только в шапке: два десятка размытых слоёв кладут
средние телефоны, и это видно на профилировании, а не в теории.

**Слабый телефон получает другую страницу.** Инлайновый скрипт в `<head>`
ставит `data-perf="low"` до первой отрисовки — по `saveData`,
`prefers-reduced-data`, объёму памяти и числу ядер в паре с сенсорным вводом
(четырёхъядерный ноутбук под это не попадает, дешёвый андроид попадает).
Дальше `assets/src/css/lowpower.css` последним слоем снимает самое дорогое:
полноэкранный SVG-шум на `feTurbulence`, бесконечную анимацию фона из четырёх
градиентов, сорок с лишним слоёв `backdrop-filter` и появление блоков при
прокрутке. Проверено в браузере: на устройстве с 2 ГБ памяти остаётся ноль
элементов с размытием. Шрифты с чужого домена больше не блокируют отрисовку —
страница рисуется системным и переключается, когда файлы доедут.

**Секции ниже экрана не раскладываются.** `content-visibility: auto` с
заданным `contain-intrinsic-size` — браузер пропускает раскладку и отрисовку
всего, до чего пользователь ещё не долистал, но полоса прокрутки остаётся
правильной длины. Появление блоков — один `IntersectionObserver`, который
отписывается от элемента сразу после показа, а не висит обработчиком скролла.

**Аналитика без третьих сторон.** Свой сборщик на Supabase: просмотры, клики,
глубина прокрутки, время внимания по секциям, воронка калькулятора. Ни одного
чужого счётчика и ни одного межсессионного идентификатора: id живёт в
`sessionStorage` и умирает вместе с вкладкой, поэтому повторный визит выглядит
как новый и баннер согласия не нужен. Публичный ключ умеет только вставлять
события и не умеет читать ничего; заявки с формы он тоже писать не может — их
принимает Edge Function под service-ключом, потому что anon-ключ лежит в
исходнике страницы. Политики на уровне строк — в `supabase/schema.sql`.
Событие отправляется через `sendBeacon`, чтобы не терялось при уходе со
страницы. Сроки хранения в политике конфиденциальности и в базе совпадают:
24 месяца на события, 36 на заявки.

## От чего я отказался

Это раздел, ради которого такие README вообще стоит читать.

**От сборщика.** Vite или Astro дали бы горячую перезагрузку и разбиение
бандлов. Здесь нечего разбивать: три CSS-файла и три JS-файла суммарно на
60 КБ. Взамен — ноль `node_modules`, ноль уязвимостей в зависимостях и сборка,
которая через три года запустится ровно так же.

**От React.** На сайте одна интерактивная штука — калькулятор проекта. Она
написана на 400 строках чистого JavaScript и работает без гидратации. React
здесь стоил бы 45 КБ рантайма ради одного визарда из шести шагов.

**От CMS.** Соблазн был, но контент правит один человек, а формат статьи —
это список кортежей в Python-файле, который читается лучше, чем интерфейс
любой headless CMS. Цена решения честная: если сайтом начнёт заниматься не
разработчик, CMS придётся вернуть.

**От единого языкового переключателя на клиенте.** Первая версия держала оба
языка в одном HTML и переключала их CSS-ом. Быстро и красиво — и ровно
половина сайта не попадала в индекс, потому что для поисковика существовал
только язык по умолчанию. Сейчас у каждой языковой версии свой URL (русская в корне, английская
в `/en/`), взаимные `hreflang` и `canonical` на себя. На главной оба языка всё ещё лежат в одном
файле (это осознанный размен ради мгновенного переключения), кроме `<h1>`: он
рендерится под язык страницы, иначе у английской версии главный заголовок
оказывался кириллицей. В блоге — раздельные страницы, потому что лонгрид
дублировать вдвое дорого.

## Что бы я сделал иначе

Честный список, потому что без него первые два раздела — реклама.

- **Фрагменты вёрстки двуязычные.** `content/fragments/*.html` содержат оба
  языка в спанах. Это наследство от первой версии; правильнее было бы вынести
  строки в словари, как сделано для кейсов и статей. Сейчас перевод главной
  требует редактировать HTML.
- **Проверки неполные.** `Tools/check.py` ловит битые ссылки, длину title и
  description, дубли `<h1>`, отсутствие canonical и hreflang и сломанный
  JSON-LD — и валит сборку в CI. Прогон axe-core пока запускается руками,
  его тоже стоило бы завести в пайплайн.
- **`content-visibility` на секциях подобран на глаз.** `contain-intrinsic-size:
  auto 700px` — среднее по больнице. Правильнее замерить фактические высоты.

Отдельно: `HANDOVER.md` — что надо заполнить руками перед публикацией
(домен, CNAME, адрес функции формы, реквизиты контролёра) и какие вопросы
остались открытыми.

## Запуск

```bash
python3 Tools/build.py          # собрать весь сайт
python3 Tools/check.py          # проверить собранное (падает при ошибке)
python3 Tools/fontcheck.py      # шрифты покрывают весь текст сайта?
python3 Tools/covers.py         # перерисовать обложки статей (обе версии)
python3 Tools/new.py post имя   # создать статью
python3 Tools/new.py case имя   # создать кейс
python3 Tools/new.py page имя   # создать страницу
python3 -m http.server 8000     # посмотреть локально
```

Зависимости: Python 3.9+ и Pillow (только для генератора обложек). Всё.

Отдельно стоит `Tools/make-webfonts.py` — он режет шрифты на подмножества и
пакует в woff2. Ему нужны fonttools и brotli, но запускается он вручную и
раз в год, когда меняются сами шрифты, поэтому в зависимости сборки не входит.

## Шрифты

Свои файлы в `assets/src/fonts/`, чужого CDN нет. Причина конкретная: до
этого заголовки набирались Archivo Black, подписи — Space Mono, оба
раздавались Google Fonts, и **ни в одном из них нет кириллицы**. Русская
половина сайта молча набиралась системным Arial и Courier New, а обложки
статей существовали только по-английски. Ошибка тихая: шрифт не падает и не
ругается, браузер подставляет системный посимвольно, и выглядит это просто
как «шрифт такой».

Теперь Unbounded Black для заголовков, JetBrains Mono для подписей, Inter
для текста — все три покрывают оба алфавита, и это проверяется:
`Tools/fontcheck.py` собирает все символы, которыми написан сайт, и сверяет
с таблицей глифов каждого файла. Латиница и кириллица лежат в разных файлах
с `unicode-range`, поэтому русский посетитель не качает латинский набор.
`@font-face` объявляет сборка (`Tools/core/assets.py`), файлы получают хеш
в имени вместе с бандлом.

Публикация — GitHub Actions (`.github/workflows/deploy.yml`): сборка,
проверка, деплой на Pages. В репозитории лежат только исходники,
собранный HTML живёт в артефакте деплоя.

Подробности по аналитике — в `supabase/schema.sql`, там же готовые запросы
для дашборда.
